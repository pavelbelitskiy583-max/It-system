# ECHOIT — IT-мастерская вашей компании

Единая система управления IT-инфраструктурой: склад, оборудование по филиалам/этажам/кабинетам,
картриджи с историей заправок, задачи, внутренний мессенджер и защищённое хранилище доступов.

Стек: **React + Vite** (фронтенд) + **Vercel Serverless Functions** (`/api`) + **Postgres**
(Vercel Postgres / Neon). Данные общие для всех сотрудников организации и хранятся в базе —
это уже не локальный прототип, а рабочая многопользовательская система.

Пароли пользователей хешируются **bcrypt**. Записи в «Доступах» шифруются **AES-GCM**
(ключ выводится из кода доступа сейфа через PBKDF2, Web Crypto API) — сервер и база данных
никогда не видят пароли/секреты в открытом виде, только зашифрованные блоки.

## Разворачивание на Vercel

### 1. Подключите базу данных

В проекте на Vercel: **Storage → Create Database → Postgres** (это Neon под капотом) →
**Connect to Project**. Vercel сам добавит переменные окружения (`DATABASE_URL` /
`POSTGRES_URL` и т.п.) в проект — ничего копировать вручную не нужно.

### 2. Добавьте секрет для сессий

В **Settings → Environment Variables** добавьте:

```
JWT_SECRET = <любая длинная случайная строка>
```

Без него сервер будет работать на небезопасном ключе по умолчанию — для продакшена задайте свой.

### 3. Передеплойте

После подключения базы и добавления `JWT_SECRET` нужен новый деплой (Vercel → Deployments →
«Redeploy»), чтобы функции подхватили переменные окружения. Таблицы в базе создаются
автоматически при первом обращении к API (идемпотентная миграция в `api/lib/db.js`) —
отдельно запускать ничего не нужно.

## Локальная разработка

Поскольку `/api` — это Vercel Serverless Functions, обычный `vite dev` их не поднимает.
Для полноценной локальной разработки (фронтенд + API + база) используйте Vercel CLI:

```bash
npm i -g vercel
vercel link      # свяжет папку с проектом на Vercel
vercel env pull  # подтянет DATABASE_URL и JWT_SECRET локально в .env.local
vercel dev
```

Если нужен только фронтенд без бэкенда (например, для правки вёрстки) — подойдёт `npm run dev`,
но авторизация и все модули работать не будут без запущенного API.

## Как пользоваться

1. На лендинге — **«Создать организацию»** (регистрация администратора).
2. **Настройки → Филиалы** — админ добавляет филиалы, этажи, кабинеты.
3. **Настройки → Сотрудники** — админ создаёт учётки: имя + логин, система генерирует пароль
   (показывается один раз — передайте его сотруднику лично) и отмечает чекбоксами доступные модули.
4. При первом входе сотрудник обязан задать собственный пароль.
5. **Доступы** — при первом открытии администратор задаёт код доступа к сейфу. Дальше у каждой
   записи (пароль / VPN / сервер / API-ключ / инструкция) можно указать чекбоксами, каким
   сотрудникам она видна — остальным она не отдаётся даже по API.

## Безопасность: что реализовано, а что стоит иметь в виду

- Сессия — JWT в httpOnly-cookie (`SameSite=Lax`, `Secure`).
- Пароли — bcrypt, соль встроена в хеш.
- Доступы — сквозное шифрование на клиенте (AES-256-GCM), сервер хранит только шифротекст;
  видимость каждой записи проверяется на сервере (не только скрывается в интерфейсе).
- Права по модулям (склад/картриджи/оборудование/задачи/мессенджер/доступы) проверяются на
  каждом API-эндпойнте, а не только в интерфейсе.
- Общий агрегированный эндпойнт `/api/state` отдаёт данные большинства модулей одним запросом
  без дополнительной фильтрации по правам (кроме раздела «Доступы», где фильтрация обязательна
  и есть). Это осознанное упрощение для MVP: сотрудник, теоретически обратившийся к API напрямую,
  минуя интерфейс, мог бы увидеть данные модулей, которые ему не открыты в UI (кроме «Доступов» —
  там сервер фильтрует всегда). Для более строгой модели `/api/state` стоит разбить на отдельные
  эндпойнты для каждого модуля с проверкой прав — это следующий шаг, если понадобится.
- Резервная копия (Настройки → Данные) отдаётся только администратору; секреты в ней
  по-прежнему зашифрованы.

## Структура проекта

```
api/
  [...path].js         — единый роутер всех serverless-эндпойнтов
  lib/
    db.js                — подключение к Postgres (Neon) + идемпотентная миграция схемы
    auth.js               — JWT-сессии, cookie, bcrypt, права доступа

src/
  context/
    AuthContext.jsx       — сессия, сотрудники, права (ходит в /api/auth, /api/employees)
    DataContext.jsx        — филиалы/склад/картриджи/оборудование/задачи/чат/сейф (ходит в /api)
  lib/
    api.js                — тонкая обёртка над fetch (JSON + cookie-сессия)
    crypto.js              — AES-GCM для сейфа (полностью на клиенте)
  layout/
    Shell.jsx               — сайдбар/топбар приложения
    Guards.jsx                — защита маршрутов (вход обязателен / права модуля / только админ)
  pages/
    Landing.jsx, Auth.jsx, Dashboard.jsx, Warehouse.jsx, Cartridges.jsx,
    Equipment.jsx, Tasks.jsx, Messenger.jsx, Vault.jsx, Settings.jsx
  components/
    Icons.jsx                 — монохромные line-art иконки
  styles.css                   — единая дизайн-система (тёмная, Sora + JetBrains Mono)
```

## Демо-медиа в hero

Видео и постер в hero используют CloudFront-ссылки из исходного макета. Замените их на
собственные в `src/pages/Landing.jsx` и `src/pages/Auth.jsx` (константы `VIDEO_URL`, `POSTER_URL`).
